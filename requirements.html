NoiseMap NYC — System Requirements
1. Introduction

1.1 Purpose

The purpose of this document is to define the user requirements and system requirements for NoiseMap NYC, a predictive noise‑mapping system designed for apartment renters in New York City. Renters typically evaluate neighborhoods based only on current noise conditions, which do not reflect how noise levels may change due to future construction, traffic variations, or seasonal activity. Chronic exposure to noise above 55 dB affects health and reduces rental value, making noise a significant decision factor.

1.2 System Overview

NoiseMap NYC predicts neighborhood noise levels 6–12 months into the future for every 50×50m grid across NYC. It integrates SONYC sensor readings, construction permits, traffic counts, zoning data, and OSM features, processed through an XGBoost model. SHAP explainability identifies contributions from construction, traffic, and baseline activity. Outputs are displayed through an interactive map with predicted noise levels, source breakdowns, and confidence indicators.

1.3 Intended Audience

  • Apartment renters seeking forward‑looking noise information before signing a lease.
  • Urban planners and city officials needing predictive insights into construction and traffic impacts.

1.4 Scope

System will do:

  • Provide predicted noise levels based on user‑input addresses
  • Predict future dB levels for selected time and lease periods
  • Generate temporal noise forecast visualisations
  • Analyse noise source contributions using SHAP
  • Display prediction confidence indicators
  • Enable comparison of multiple neighbourhoods
  • Calculate noise exposure overlap during lease period
  • Estimate noise variation by floor level

System will NOT do:

  • Predict unpredictable human activities
  • Provide real‑time indoor noise monitoring
  • Guarantee future noise outcomes
2. User Requirements

2.1 Stakeholders

Primary Users

  • Apartment renters — want future noise predictions; care about accuracy and clarity.
  • First‑time renters — need simple, plain‑language explanations.

Secondary Users

  • Urban researchers — care about transparency and model reliability.

External Data Providers

  • NYC Open Data
  • NYC Department of Buildings
  • NYC Department of Transportation
  • NYC SONYC

Internal Stakeholders

  • Development team — need clear requirements and feasible scope.

2.2 User Requirement Statements

  • System shall allow a user to enter an address and receive noise predictions up to 12 months.
  • System shall display predictions in simple language for non‑technical users.
  • System shall identify dominant noise sources using badges.
  • System shall allow users to enter lease duration and view noise changes.
  • System shall allow comparison of two neighbourhoods.
  • System shall indicate prediction reliability.
  • System should communicate whether noise is temporary (e.g., construction).
  • System will rely only on public open‑source data.
  • System shall clarify noise impact using health studies.

2.3 Constraints

Operational Constraints

  • System shall operate as a web‑based application.
  • System shall be accessible on desktop and mobile browsers.
  • System shall not require login.
  • System shall estimate financial impact on rent.

Data Constraints

  • System shall use only public open data.
  • System shall not store personal information.
  • Predictions shall not be presented as guaranteed outcomes.
  • Predictions shall include confidence indicators.

Scope Constraints

  • No real‑time noise monitoring.
  • NYC only.
3. System Requirements Specification

3.1 Functional Requirements

  • System shall display current and future predicted noise levels.
  • System shall compare multiple properties simultaneously.
  • System shall visualize noise using intuitive methods (heatmaps, scales).
  • System shall identify noise sources (traffic, construction, airplanes).
  • System shall allow filtering by noise tolerance.
  • System shall provide notifications for unusual noise changes.
  • System shall explain technical data in simple terms.

3.2 Non‑Functional Requirements

Product Requirements

  • Moderate noise should be labeled neutrally.
  • System must explain why noise matters.
  • System must clarify what it can and cannot predict.
  • Predictions must distinguish sensor‑based vs complaint‑based data.
  • Temporary vs permanent noise must be clearly differentiated.

Organizational Requirements

  • System must be built using Python, Pandas, GeoPandas, XGBoost, SHAP, Streamlit, PyDeck.
  • NYC only.
  • Prediction horizon fixed at 12 months.
  • Grid resolution fixed at 50×50m.
  • Model must be validated on a held‑out test set.

External Requirements

  • System must reference research studies to support predictions.
  • 311 complaint bias must be acknowledged.
  • No data may identify individual residents.
4. Requirement Elicitation

Scope of Elicitation

Activities aimed to understand:

  • How renters evaluate noise before signing a lease
  • Importance of noise in rental decisions
  • Most concerning noise sources
  • Trust conditions for predictive tools
  • Preferred display formats

Elicitation Methods

  • Survey (28 respondents)
  • Interviews (12 participants)
  • Expert interview (ISSE professor)
5. Key Findings

Expert Interview Findings

  • Night‑time noise is most critical for housing decisions.
  • Current assessment relies on physical visits.
  • Supports property comparison and tolerance settings.

Noise in Rental Decisions

  • Noise moderately important but not top priority.
  • Most rely on single visits.

Current Limitations

  • Noise discovered only after moving in.
  • Main unexpected sources: traffic, construction, neighbours.

Health Awareness

  • 50% unaware of 55 dB health risks.
  • Common impacts: sleep disruption, stress.

Trust in Predictive Tools

  • 40% trust predictions; 40% unsure.
  • Trust increases with transparency.

Display Preferences

  • Heatmaps
  • Noise scores
  • Time‑of‑day breakdown
6. Derived Requirements

Confirmed Requirements

  • Display prediction confidence and data sources
  • Include health context
  • Use plain‑language labels
  • Prioritize traffic, construction, sensor data

Proposed Requirements

  • Forward‑looking predictions
  • Heatmap + score visualization
  • Time‑of‑day patterns
  • Transparent data sources
  • Identify key noise sources
  • Distinguish temporary vs long‑term noise
  • Support comparison
  • User‑adjustable tolerance
7. Key Assumptions
  • Noise is not always top rental factor
  • Complaint datasets may be biased
8. Open Issues
  • Availability of nightlife and insulation datasets
  • Feasibility of time‑of‑day prediction
  • Sensor coverage adequacy
  • Scope of share function
